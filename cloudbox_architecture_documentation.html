01. Project Overview

CloudBox is a production-grade, distributed self-hosted personal cloud storage ecosystem engineered as a TypeScript monorepo using pnpm workspaces. Instead of forcing users to store files on centralized third-party servers, CloudBox enables users to register their own local devices (PC, Home Server, Raspberry Pi) as remote storage nodes via a lightweight Node.js CLI agent. The platform provides a modern Next.js 16 Web Dashboard, an Express REST API backend, an event-driven WebSocket Gateway for tunneling file chunks across NATs/firewalls via RSA-signed authentication, a PostgreSQL database managed via Prisma ORM, and a Redis pub/sub backbone for inter-service RPC coordination.

One-Line Explanation

A hybrid cloud-edge storage platform that turns personal machines into secure, remote storage nodes accessible through a centralized web dashboard and WebSocket gateway.

What Problem Does It Solve?

  • Problem: Cloud storage providers (Dropbox, Google Drive, OneDrive) are expensive, enforce strict storage caps, and hold user privacy at risk. Traditional self-hosted solutions (like Nextcloud or NAS) require complex port forwarding, static public IPs, or dynamic DNS setups to access storage outside the home network.
  • Target Users: Developers, homelab enthusiasts, remote teams, and privacy-conscious users who want centralized cloud access to decentralized storage hardware.
  • Main Purpose: Provide zero-configuration NAT traversal for personal storage nodes, allowing secure remote file uploads, downloads, streaming, trash recovery, versioning, and public sharing over standard HTTPS/WSS.

03. Service-by-Service Breakdown

1. Main API Backend (apps/api)

  • Responsibility: HTTP REST endpoints, user authentication, workspace administration, file metadata database operations, email dispatch, and initiating file streaming commands over Redis.
  • Entry Point: apps/api/src/index.ts & apps/api/src/app.ts
  • Key Files:
    • routes/auth.ts: User registration, login, JWT cookie management, Google OAuth callback, email OTP verification.
    • routes/files.ts: File upload (busboy streaming), download tunnel, soft-delete, restore, permanent wipe, version query.
    • routes/agents.ts: Claim code generation (Redis 10m TTL), agent registration endpoint.
    • routes/admin.ts: Workspace user/agent quota allocation, role assignments, audit logs.
    • lib/gatewaySubscriber.ts: Listens on Redis channel gateway:responses, executes DB reconciliation algorithm for METADATA_SYNC.
    • lib/requestRegistry.ts: Singleton EventEmitter that maps async Redis chunk events to pending HTTP response streams via requestId.
  • Scaling: Horizontally scalable behind Nginx. It is completely stateless with respect to file uploads/downloads because all session state lives in JWT HTTP-only cookies and inter-service state is synchronized via Redis.

2. WebSocket Gateway (apps/gateway)

  • Responsibility: Maintains persistent TCP WebSocket connections with remote Storage Agents. Handles RSA cryptographic challenge authentication, sends periodic pings (30s interval), routes file commands from API to Agents, and publishes Agent responses back to Redis.
  • Entry Point: apps/gateway/src/index.ts
  • Key Files:
    • auth.ts: Performs 3-step handshake: Sends 32-byte hex challenge, receives base64 RSA signature, verifies with stored Public Key using Node crypto.
    • heartbeat.ts: Runs 30s setInterval ping. Terminates sockets and marks agents OFFLINE if silent for >65s.
    • relay.ts: Subscribes to Redis channel gateway:commands and publishes to gateway:responses.
    • registry.ts: In-memory Map<string, SocketEntry> mapping cloudId to live WebSocket objects.
  • Scaling: Single-instance per Gateway instance by default due to in-memory socket registry. Can scale horizontally if an upstream router routes by cloudId or by adopting Redis WebSocket socket registry adapter. (INFERENCE)

3. Storage Node Agent (apps/agent)

  • Responsibility: Executable Node CLI tool running on remote hardware. Connects via outbound WSS to Gateway, signs auth challenges with local private key, watches local directory ~/.cloudbox/storage with chokidar, and executes chunked file read/write disk I/O.
  • Entry Point: apps/agent/src/index.ts
  • Key Files:
    • watcher.ts: Uses chokidar to watch local files with 1-second debounce. Scans recursive tree, computes MIME types, generates relative path metadata array.
    • index.ts: CLI setup via commander. Implements register and start commands. Manages backoff reconnection (1s to 30s exponential). Reads files via 64KB chunks (fs.createReadStream) and writes incoming base64 chunks via fs.createWriteStream.

04. Complete Data Flows

Flow A — User Signup & Email OTP Verification (VERIFIED)

  1. User submits email, password, and workspace option (create workspace or invite code) to POST /auth/signup.
  2. auth.ts validates inputs via Zod, checks email uniqueness in Prisma, hashes password with argon2.hash().
  3. If creating workspace: creates User (role=ADMIN) and nested Group in PostgreSQL, updates user groupId.
  4. If joining: verifies inviteCode in Group table, creates User (role=USER, groupId linked).
  5. System generates cryptographically random 6-digit OTP using crypto.randomInt(), stores it in Redis at email_otp:<userId> with 600s TTL.
  6. Nodemailer sends HTML email containing OTP via Brevo SMTP (smtp-relay.brevo.com:587). Returns { requiresVerification: true } to frontend.
  7. User submits OTP to POST /auth/verify-email. emailOtp.ts compares code with Redis value. On match, deletes Redis key, updates user emailVerified: true in PostgreSQL, and sets HTTP-only auth cookies.

Flow B — Agent Cryptographic Claim & Registration (VERIFIED)

  1. Authenticated user clicks "Add Storage Node" in Web Dashboard. Frontend calls POST /agents/claim.
  2. API generates 6-character hex code using crypto.randomBytes(3), sets Redis key claim:<hexCode> = userId (600s TTL).
  3. User runs CLI command on remote node: cloudbox-agent register <CODE>.
  4. Agent generates 2048-bit RSA keypair (SPKI public key PEM, PKCS8 private key PEM) and a random UUID cloudId.
  5. Agent posts { claimCode, cloudId, publicKey } to POST /agents/register on API.
  6. API fetches userId from Redis key claim:<claimCode>. If valid, creates row in agents table (status=OFFLINE, stores RSA public key). Deletes Redis key. Agent saves config to ~/.cloudbox/agent.json.

Flow C — File Upload Pipeline (Browser → API → Gateway → Agent Disk) (VERIFIED)

  1. User selects file in dashboard and posts to POST /files/upload?folder=/path&agentId=...
  2. API checks user storage quota (usedBytes + expectedSize <= quotaBytes). Resolves target agent, ensuring status is ONLINE and lastHeartbeat > 2 mins ago.
  3. API initializes Busboy multipart stream parser and generates a requestId (UUID).
  4. API sends Redis command to channel gateway:commands: { type: "UPLOAD_FILE", path, requestId }. Gateway relays payload to Agent WebSocket. Agent initializes local fs.createWriteStream at ~/.cloudbox/storage/path.
  5. As browser streams bytes into API, Busboy reads file chunks. API slices buffer into 64KB segments, encodes to base64, and publishes FILE_CHUNK commands to Redis. Gateway relays each chunk to Agent over WebSocket.
  6. Agent receives FILE_CHUNK, converts base64 back to binary Buffer, and writes to disk stream.
  7. When browser upload completes, API publishes FILE_CHUNK with final: true. Agent closes write stream, triggers local scanDirectory(), and sends UPLOAD_ACK over WebSocket.
  8. Gateway publishes UPLOAD_ACK to Redis gateway:responses. GatewaySubscriber in API receives ACK and emits event to requestRegistry singleton using requestId.
  9. API handler unblocks, increments user usedBytes in PostgreSQL, creates snapshot row in file_versions table if file previously existed, checks 80%/95% quota warning thresholds, and returns HTTP 200 JSON.

Flow D — Real-Time Metadata Sync (Agent → Gateway → API DB Reconciliation) (VERIFIED)

  1. Agent directory watcher (chokidar) detects file addition, modification, or deletion in ~/.cloudbox/storage.
  2. Watcher debounces events for 1000ms, scans directory recursively using fs.readdirSync(), and formats ScanResult[] array.
  3. Agent sends METADATA_SYNC message over WebSocket to Gateway. Gateway publishes message to Redis gateway:responses.
  4. API GatewaySubscriber picks up payload and executes 2-Pass Reconciliation Algorithm (syncAgentFiles):
    • Pass 1: Directory Synthesis & Diffing: Synthesizes parent folder paths missing from scan. Fetches existing files from PostgreSQL. Deletes files missing from scan. Upserts files whose size, mtime, or MIME type changed.
    • Pass 2: Tree Relinking: Queries updated files, resolves parent directory paths, and updates parentId foreign keys to construct exact directory hierarchy.

What happens if Redis goes down?
If Redis crashes, critical HTTP auth and CRUD operations reading/writing to PostgreSQL continue to function. However, realtime Agent communications (file uploads/downloads, live metadata syncs, and CLI claim code registrations) will fail immediately because inter-service RPC depends on Redis Pub/Sub channels.

08. Core Business Logic / Algorithms

2-Pass Directory Tree Reconciliation Algorithm

Problem: When an Agent scans its local file directory, it returns a flat list of file paths (e.g., ["/docs/work/file.txt"]). The database requires a relational hierarchy with correct parentId references pointing to parent directory records, while handling concurrent file additions, edits, and deletions.

Location: apps/api/src/lib/gatewaySubscriber.ts -> syncAgentFiles()

Step-by-Step Logic:

  1. Path Synthesis: Iterates over incoming paths. Synthesizes missing intermediate directory records (e.g., automatically inserts /docs and /docs/work if missing from payload).
  2. Differential Deletion: Queries all existing files in PostgreSQL for the current agentId. Identifies files present in DB but absent from scan payload and executes batch deleteMany().
  3. Attribute Upserting: Compares size, modification timestamp (mtime), and MIME type between incoming scan items and DB records. Executes atomic updates for modified files or creates new File rows.
  4. Parent Link Reconstruction (Pass 2): Queries all database files for the agent. Computes exact parent folder paths, maps parent paths to directory IDs, and updates parentId foreign keys across all records.

Complexity: Time Complexity: $O(N \log N)$ where $N$ is the number of files (due to Map lookups and sorting). Space Complexity: $O(N)$ memory footprint to store current file tree maps.

09. Concurrency & Asynchronous Processing

  • Node.js Event Loop: Non-blocking single-threaded asynchronous execution using async/await, Promises, and Node streams.
  • Request Synchronization via EventEmitter: The API handles asynchronous file stream chunks using RequestRegistry (an EventEmitter instance with setMaxListeners(500)). HTTP requests wait for matching requestId events emitted by the Redis Gateway subscriber.
  • Race Condition Prevention:
    • PostgreSQL unique compound constraint @@unique([agentId, path]) prevents duplicate file paths per storage node under concurrent uploads.
    • Prisma atomic increment operators (usedBytes: { increment: expectedSize }) prevent race conditions on user storage quota calculations.

Heartbeat Mechanism

The Gateway runs a 30-second heartbeat loop (heartbeat.ts). If an agent fails to respond to pings for 65 seconds (>2 missed pings), the Gateway terminates the socket connection, unregisters it from memory, updates PostgreSQL status = "OFFLINE", and publishes an AGENT_OFFLINE event trigger to email the owner.

15. Why This Technology?

PostgreSQL vs MongoDB

Decision: PostgreSQL was chosen. (VERIFIED FROM CODE)

Reason: CloudBox file hierarchies rely heavily on relational constraints (foreign keys for parentId, userId, agentId) and transactional integrity when updating storage quotas (usedBytes). MongoDB lacks enforcement of strict foreign key referential integrity required for safe cascading file deletions.

Redis Pub/Sub vs RabbitMQ / Kafka

Decision: Redis Pub/Sub was chosen. (INFERENCE)

Reason: CloudBox requires low-latency ephemeral RPC message routing between the API and Gateway to forward live base64 file chunks. Heavy persistent message queuing (like Kafka or RabbitMQ) introduces unnecessary operational overhead, whereas Redis provides instant pub/sub primitives alongside key-value TTL storage for claim codes and OTPs.

16. Docker & Containerization

The system is orchestrated via docker-compose.yml defining 5 main services (PostgreSQL, Redis, API, Gateway, Web) and 4 observability services (Prometheus, Loki, Promtail, Grafana under profile observability).

Startup Sequence (docker compose up):

  1. PostgreSQL & Redis start first with healthchecks (pg_isready and redis-cli ping interval 5s).
  2. API container builds from root context (multistage Dockerfile), waits for Postgres & Redis healthchecks to pass, runs Prisma migrations, and binds port 4000.
  3. Gateway container builds, connects to Redis, executes startup cleanup (resets stale ONLINE agents to OFFLINE), and binds port 4001.
  4. Web container builds Next.js production bundle and binds port 3000.

19. Scalability Analysis

  • Current Bottlenecks:
    1. Memory footprint of base64 chunking during large file transfers.
    2. Gateway WebSocket registry is stored in local Node.js process memory (Map<cloudId, WebSocket>), preventing multi-instance Gateway horizontal load balancing without sticky sessions.
  • Horizontal Scaling Plan: Replace local Gateway memory registry with a Redis-backed WebSocket connection lookup table or sticky routing on Nginx based on cloudId header.

20. Failure Scenarios

Failure EventCurrent System BehaviorData ImpactSystem Recovery
Agent Disconnects / Crashes Gateway heartbeat times out after 65s, sets status OFFLINE, triggers email notification. Zero data loss. Local files remain intact on agent disk. Agent CLI auto-reconnects with exponential backoff (1s to 30s) and triggers full sync upon auth.
API Gateway Crash Mid-Upload Browser upload fails with HTTP error. Agent stream times out and deletes partial buffer. Partial upload abandoned; database state unchanged. Docker restart policy (unless-stopped) restores container in seconds. User retries upload.

22. "Why Not X?" Interview Questions

Why not store files on AWS S3 directly?

Answer: CloudBox is designed specifically to eliminate third-party cloud storage fees and privacy concerns by allowing users to leverage their existing local hardware (NAS, desktop hard drives) while enjoying cloud-like web access.

Why use a separate Gateway service instead of handling WebSockets in Express?

Answer: Separating the Gateway decouples long-lived persistent TCP WebSocket state management from the stateless HTTP REST API. This allows the Express API to scale horizontally without severing active agent connections.

23. Technical Interview Q&A

Q: How do you prevent an unauthorized device from registering as a user's storage node?

Answer: Registration requires a 2-step process. First, an authenticated user generates a short-lived (10-min TTL) 6-character claim code stored in Redis. The remote device submits this code along with a generated 2048-bit RSA public key. Furthermore, every subsequent WebSocket connection requires the agent to sign a random 32-byte cryptographic challenge string using its RSA private key, verified against the public key saved during registration.

Q: How does the system handle file synchronization when a file is modified locally on the Agent machine?

Answer: The Agent uses chokidar to monitor file system events in ~/.cloudbox/storage. When a change occurs, it debounces for 1 second, scans the directory, and sends a METADATA_SYNC payload over the WebSocket. The API's GatewaySubscriber receives this via Redis and executes a 2-pass reconciliation algorithm that updates timestamps, recalculates parent folder IDs, and updates database metadata automatically.

1. Gateway Cryptographic Handshake (apps/gateway/src/auth.ts)

export async function runAuthHandshake(ws: WebSocket): Promise<string | null> {
  const challenge = randomBytes(32).toString("hex");
  send(ws, { type: "AUTH_CHALLENGE", challenge });

  // Wait for AUTH_RESPONSE from agent
  const handler = async (raw: Buffer | string) => {
    const msg = JSON.parse(raw.toString());
    if (msg.type !== "AUTH_RESPONSE") return;

    const { cloudId, signature } = msg;
    const agent = await prisma.agent.findUnique({ where: { cloudId } });
    if (!agent) return resolve(null);

    const verify = createVerify("SHA256");
    verify.update(challenge);
    const isValid = verify.verify(agent.publicKey, signature, "base64");

    if (!isValid) return resolve(null);
    await prisma.agent.update({ where: { cloudId }, data: { status: "ONLINE" } });
    registerSocket(cloudId, agent.id, ws);
    resolve(cloudId);
  };
  ws.on("message", handler);
}

2. Async Request Waiter (apps/api/src/lib/requestRegistry.ts)

class RequestRegistry extends EventEmitter {
  waitFor<T>(requestId: string, timeoutMs = 30_000): Promise<T> {
    return new Promise((resolve, reject) => {
      const timer = setTimeout(() => {
        this.off(requestId, handler);
        reject(new Error(`Request timed out: ${requestId}`));
      }, timeoutMs);

      const handler = (data: T) => {
        clearTimeout(timer);
        resolve(data);
      };
      this.once(requestId, handler);
    });
  }
}

25. Complete End-to-End Scenario

Scenario: User downloads a 10MB video file

  1. User clicks "Download" in Next.js web dashboard. Browser issues GET /api/files/download/:id with HTTP-only cookie.
  2. Express filesRouter authenticates JWT payload, checks file existence and user permissions in PostgreSQL.
  3. API checks agent status. If lastHeartbeat > 2 mins ago, rejects with 503 node offline.
  4. API generates UUID requestId, sets response headers (Content-Disposition, Content-Type), and publishes DOWNLOAD_FILE command to Redis channel gateway:commands.
  5. Gateway subscriber routes command over active WebSocket to target Agent.
  6. Agent receives command, opens fs.createReadStream with 64KB chunk size. Iterates over stream, base64 encodes each chunk, and sends FILE_CHUNK WebSocket messages to Gateway.
  7. Gateway publishes each chunk to Redis channel gateway:responses.
  8. API GatewaySubscriber receives chunk and emits to requestRegistry using requestId.
  9. API download route handler receives chunk, decodes base64 back to binary Buffer, and writes to Express response stream (res.write(buffer)).
  10. Agent sends final chunk (final: true). API closes HTTP response stream (res.end()). Browser completes download.

The core problem it solves is allowing privacy-focused users to turn their local storage devices—like a home PC or Raspberry Pi—into a private cloud accessible through a web browser without complex network configurations like static IPs or port forwarding.

Architecturally, it consists of three primary application layers: a modern React 19 web interface, a stateless Express API backend, and a real-time WebSocket Gateway. Users run a lightweight Node.js CLI Agent on their local storage device. To register a node, the agent generates an RSA-2048 keypair and claims a 6-character code managed in Redis. When the agent connects to the Gateway over WebSocket, the server verifies a cryptographic challenge signature before marking the device online.

When a user uploads a file, the API processes incoming HTTP multipart streams via Busboy, breaks the file into 64KB base64 chunks, and publishes commands over Redis Pub/Sub. The Gateway relays these chunks down the WebSocket tunnel to the Agent, which writes them directly to disk. The Agent continuously monitors disk changes with Chokidar and executes a two-pass tree reconciliation algorithm to sync directory metadata back to PostgreSQL. The whole platform is containerized with Docker Compose and deployed on AWS EC2 behind Nginx with Let's Encrypt SSL."
